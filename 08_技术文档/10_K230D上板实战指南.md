## 三、⚠️⚠️ 最重要的踩坑记录：必须按 KEY2 启动

**这是本阶段最大的坑，也是最花时间的部分。**

### 现象与原因对照

| 现象 | 原因 |
|---|---|
| LCD 显示**可交互桌面**（Photos/Settings/AI Hub…） | 这是 **SD NAND 里固件**的开机程序 |
| 串行终端**空白、无 `>>>`** | SD NAND 固件**没有把 REPL 交给 CanMV IDE** |
| IDE 点"停止"卡在**"忙碌中…请稍候"** | 桌面程序未调用 `os.exitpoint()`，**IDE 抢不到控制权** |
| 滑屏时 IDE 帧缓冲区**同步变化** | `to_ide` 投屏正常，只是画面源是那个桌面 |
| 串行终端无任何脚本输出 | 脚本**根本没被执行**（REPL 未就绪） |

### 根因

**本项目烧录的是 `_tf.img`（TF 卡启动版固件）**，而 **K230D BOX 复位后默认从板载 SD NAND 启动**。
SD NAND 里的固件带桌面环境、且不把 REPL 交给 IDE，所以 IDE 无法上传/运行脚本。

### ✅ 正确操作（每次都要）

```
1. 按住 KEY2 不放
2. 单击【复位按键】
3. 松开 KEY2
   → 从 TF 卡启动 → REPL 就绪（串口出现 >>>）
   → CanMV IDE 才能上传并运行脚本
```

**验证成功的标志**（串行终端应出现）：

```
>>>
MPY: soft reboot
CanMV 0295137e6(based on Micropython e00a144) on 2025-09-20; k230d_canmv_atk_dnk230d with K230D
```

### 衍生问题：每次都要按键，烦

| 方案 | 操作 | 优缺点 |
|---|---|---|
| **A. 保持现状** | 每次按 KEY2 | ✅ 不动 SD NAND<br>❌ 每次要按键（含脱机） |
| **B. 把 `_tf.img` 烧到 SD NAND** | K230BurningTool，目标介质选 **EMMC** | ✅ 免按键<br>❌ 覆盖出厂固件 |

> ⚠️ 方案 B 会覆盖出厂固件。**建议项目做完前先不动**，用方案 A。

## 八、⭐ kmodel 转换的 5 个大坑（**本次实测全部踩过**）

这些是 **2026-10-11 实际转换时遇到的**，每个都花了时间排查。记录下来，避免重蹈覆辙。

### 坑 1：下载了错误的文件（连字符 vs 下划线）

GitHub v2.11.0 的 Assets 里有**两个极易混淆**的文件：

| 文件名 | 大小 | 是什么 |
|---|---|---|
| `nncase-2.11.0-cp312-cp312-win_amd64.whl` | 18.75 MB | 编译器**本体**（PyPI 上就有） |
| **`nncase_kpu-2.11.0-py2.py3-none-win_amd64.whl`** | **1.27 MB** | ⭐ **KPU 插件（真正需要的）** |

**区别在分隔符**：`nncase-` 是本体，`nncase_kpu-` 才是插件。
**症状**：装完插件仍然报 `The given key 'k230' was not present in the dictionary`（k230 target 未注册）。
**正确做法**：PyPI 装 `nncase` 本体，GitHub 单独下 **1.27 MB 的 `nncase_kpu`**。

### 坑 2：`nncase_kpu` 用 pip 装会失败

```
ERROR: Invalid requirement: 'nncase==kpu': Expected end or semicolon
```

**原因**：pip 把文件名 `nncase_kpu-2.11.0-py2.py3-none-win_amd64.whl` 按 PEP 503 规范化后理解成了 `nncase==kpu`（把 `_kpu` 当成了版本号）。
**解决**：**用一个小的 Python 解包脚本直接释放到 `site-packages`**，绕过 pip：

```python
import zipfile
zipfile.ZipFile(r'<wheel路径>').extractall(r'<site-packages路径>')
```

**验证成功**：`nncase/modules/kpu/Nncase.Modules.K230.dll` 存在，且设置 `target='k230'` 后 `Compiler()` 不再抛异常。

### 坑 3：numpy 2.x 的 `repr()` 破坏 mean/std 传递

```
System.FormatException: The input string 'np.float32(0.485)' was not in a correct format.
  at Nncase.Compiler.Interop.CApi.StringToArrayFloat(String value)
```

**原因**：`co.mean = list(MEAN)` 得到的仍是 **numpy 标量**。numpy 2.x 的 `repr()` 会输出 `np.float32(0.485)`，而 nncase 底层要按浮点字符串解析 → 失败。
**解决**：强制转 Python 原生 float：

```python
co.mean = [float(x) for x in MEAN]
co.std  = [float(x) for x in STD]
```

> 💡 这是 **numpy 2.x 与 nncase 的兼容问题**。若改用 numpy 1.x 也不会触发。

### 坑 4：校准数据的 dataset 维度多包了一层

```
System.ArgumentException: Dataset count 1 not equals to params count 1 * samples count 400
```

**原因**：`calib` 形状已是 `(N,1,3,224,224)`（自带 dataset 维度）。写成 `[calib]` 或 `[(calib,)]` 会再包一层，被 nncase 当成"1 个 dataset"。
**实测可行的三种格式**：

| 格式 | 写法 | 结果 |
|---|---|---|
| D | `[calib]` → 不行；`calib` 直接传 | ✅ 可行 |
| **E** | **`[(calib[i],) for i in range(N)]`** | ✅ **可行（推荐，语义清晰）** |
| F | `[[x] for x in calib]` | ✅ 可行 |
| B | `[(calib,)]` | ❌ 样本数不符 |
| G | `[[[x]] ...]` | ❌ TypeError |

### 坑 5：校准数据 dtype 必须是 uint8，不能提前归一化

```
System.InvalidOperationException: Feed Value Is Invalid,
  need u8[1,3,224,224] but get f32[1,3,224,224]!
```

**原因**：脚本设了 `co.preprocess = True`，**nncase 会在编译时用 `co.mean`/`co.std` 自己归一化**。若校准集又提前做了 `(a-mean)/std` 并转成 float32，就会冲突。
**解决**：校准集必须是**原始 uint8 像素**：

```python
arr = np.zeros((N, 1, 3, size, size), dtype=np.uint8)   # 不是 float32
...
arr[k, 0] = np.asarray(im, dtype=np.uint8).transpose(2, 0, 1)   # 不除 255、不减 mean
```

> **一句话总结坑 4+5**：`co.preprocess=True` 时，校准集要喂**原始 uint8 图**，格式是 **N 个单元素元组** `[(img0,), (img1,), ...]`。

## 九、⭐ 反直觉发现：ONNX 动态量化"体积小了但更慢"

> 场景：为便于把工具打包分发给队友，想压缩 97 MB 的 ONNX 模型。
> 用 `onnxruntime.quantization.quantize_dynamic` 做了 INT8 动态量化，结果出乎意料。

### 实测数据

| 指标 | FP32 原版 | **INT8 动态量化版** | 变化 |
|---|---|---|---|
| 体积 | 97.41 MB | **24.53 MB** | ↓ 压到 **25.2%** ✅ |
| Top-1 一致率（40 类各 1 张） | — | **40 / 40（100%）** | ✅ 判断完全没变 |
| Top-1 概率偏差 | — | 最大 **33 个百分点** | ⚠️ 置信度值不可靠 |
| **CPU 推理耗时** | **114 ms** | **587 ms** | ❌ **慢了 5.1 倍** |

### 为什么量化后反而更慢？

**动态量化（dynamic quantization）只量化权重，不量化激活**：

```
权重 INT8  ──反量化──►  FP32  ──卷积──►  输出
              ↑
        每层都多这一步，卷积本身仍是浮点运算
```

- **体积**：权重从 FP32 变 INT8 → 确实小 4 倍 ✅
- **速度**：卷积核仍需浮点计算，**额外的反量化开销反而拖慢了 CPU 推理** ❌

> **量化提速的前提是硬件有 INT8 加速指令**（如 KPU、VNNI 指令集）。
> 在普通 CPU 上做动态量化，**只有减体积，不一定有提速**。

### 对我们的两个决定

| 决定 | 理由 |
|---|---|
| **K230D 上用 INT8**（25.87 MB kmodel） | 因为 **KPU 有 INT8 硬件加速**（实测 28 FPS） |
| **PC 端分发包仍用 FP32**（97 MB） | 保住 **114 ms** 的速度和可靠的置信度 |

### 这条发现的价值

它是 [13_技术路线思考.md](<13_技术路线思考.md>) 的一个具体注脚：

> **同一个"量化"动作，在端侧 NPU 上是加速，在 PC 的 CPU 上却是减速。**
> **不存在"通用的最优技术"，只有"匹配硬件特性的技术"。**

> 复现方式：见 `02_代码_模型训练/deploy_check.py`（量化前后逐张一致性比对）
> ⚠️ 注意：该脚本必须在 ASCII 临时目录中执行 —— onnxruntime 量化工具会生成
> `-inferred.onnx` 中间文件，**中文路径会 FileNotFoundError**（我们的老坑）。

| C. 只发代码，模型让队友自己下 | 50 KB | 要去下 97 MB 模型 | ❌ 麻烦且易出错 |

### 分发包结构（已实测可用）

```
车辆识别工具/
├── start.bat              ← 队友双击这个（纯 ASCII，防 GBK 乱码）
├── 使用说明.md
├── requirements.txt
├── 打包.py                ← 重新打包用
├── agent/                 ← 代码（约 50 KB）
│   ├── server.py / agent_core.py / tools.py / config_loader.py
│   ├── config.ini         ← 密钥
│   └── static/index.html
└── models/                ← 模型与标签
    ├── cars1000_resnet50_224.onnx   （97.41 MB）
    ├── class_names_cn.txt / class_names_en.txt
    └── class_taxonomy.csv
```

**打出来 90.43 MB 的 zip**（微信单文件上限 1 GB，可行）。

### 为分发做的 4 处工程改进

| 改进 | 解决的问题 |
|---|---|
| **模型路径自动探测**（`models/`、`deploy/`、同目录都试） | 开发结构与分发结构不同，同一份代码两处都能跑 |
| **`start.bat` 纯 ASCII** | GBK 系统下中文 bat 会乱码（详见本文件坑记录） |
| **自动安装依赖** | 队友不必手动 pip |
| **Python 缺失时给明确指引** | 提示要勾 `Add python.exe to PATH` |
